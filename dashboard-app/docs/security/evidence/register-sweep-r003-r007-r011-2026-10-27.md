## R-003 — host-header validation

**Claim in the register:** control released 2026-10-20 (PR #4, deploy `6ad70e11`) and verified in
production; not closed only because independent review is waived.

The earlier verification exercised production only, where Netlify's edge sits in front of the app.
That cannot distinguish "the app rejected the header" from "the app never received it", so the
control itself was never proven. Re-measured in two places.

| Probe | Result |
| --- | --- |
| Production `GET /auth/login`, `Host: evil.example.com` | **404** `Not Found - Request ID: …` — rejected by the edge, the app is never reached |
| Production `GET /auth/login`, `X-Forwarded-Host: evil.example.com` (valid `Host`) | **200** |
| Production control (no forged headers) | **200** |
| **Local app**, `X-Forwarded-Host: evil.example.com` | **400 `Bad Request: unrecognised host.`** |
| **Local app**, `Host: evil.example.com` | **400 `Bad Request: unrecognised host.`** |
| Local app control | **200** |

**Conclusion.** The application-layer control works: given a forged header it rejects with 400, and it
does not reject legitimate traffic. Production's 200 for a forged `X-Forwarded-Host` means the edge
**replaces or strips that header before the app sees it** — the app is not accepting a forged value.
There is no evidence of a gap, and two independent layers exist.

**Limitation, stated:** from outside, "the edge strips it" and "the edge overwrites it" are
indistinguishable, and this record does not claim which. It does not matter for the risk: in neither
case does the app observe an attacker-controlled value. Proving which would require header echo inside
the deployment, which is itself a new surface and was not added.

**M8:** independent human review remains **WAIVED under D5 — waived, not satisfied**. Closing this
entry closes the *control question*, not the review obligation.

## R-011 — explicit Solana RPC per context

The register's one residual was that production carried **no** explicit `SOLANA_RPC_URL`, resolving to
a code default. Fixed by configuration, no code change.

```
netlify env:set SOLANA_RPC_URL https://api.mainnet-beta.solana.com --context production
```

Read back per context with `netlify env:get SOLANA_RPC_URL --context <ctx>`:

| Context | Before | After |
| --- | --- | --- |
| `production` | *(no value)* | `https://api.mainnet-beta.solana.com` |
| `deploy-preview` | `https://api.devnet.solana.com` | unchanged |
| `branch-deploy` | `https://api.devnet.solana.com` | unchanged |

Netlify reported: *"Changes will require a redeploy to take effect on any deployed versions."*
**So the configuration is what is now closed; the running production deployment will not read the new
value until the next deploy.** This is recorded rather than glossed: the risk was "the constraint is
convention, not configuration", and that is now resolved.

Related: the browser CSP no longer lists `api.devnet.solana.com` at all (R-017), because the browser is
mainnet-pinned and never used devnet.
